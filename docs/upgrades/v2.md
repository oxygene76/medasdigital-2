# medasdigital-2 software upgrade "v2" (security upgrade)

**Upgrade name:** `v2`
**Upgrade height:** set by the governance proposal. Check it with
`medasdigitald q upgrade plan`.
**Type:** security upgrade. No new features, no parameter or state changes.
The upgrade handler only runs the module migrations, which are no-ops because
no module version changes.

v1.0.1 cannot process blocks from the upgrade height on, and v2 refuses to run
before it. **All validators must switch binaries at the upgrade height.**

## 1. Versions

| Component | v1.0.1 (current) | v2 | Why |
|---|---|---|---|
| Cosmos SDK | v0.50.10 | **v0.50.15** | last v0.50 release (the v0.50 line is end of life) |
| ibc-go | v8.5.1 | **v8.8.0** | last v8 release |
| CometBFT | v0.38.21 | **v0.38.26** | last v0.38 release |
| wasmd | v0.53.0 | **v0.54.10** | last wasmd release line for Cosmos SDK v0.50 with current security fixes |
| wasmvm / libwasmvm | v2.1.2, dynamic (`/lib/libwasmvm.x86_64.so`) | **v2.2.9, statically linked** | the 2.1 line is no longer maintained |
| Go | 1.22.11 | **1.26.8** | wasmd v0.54.10 requires Go ≥ 1.23.2; Go 1.26 is a supported Go line |
| Binary | dynamic (glibc) | **static (musl)** | does not use the system libwasmvm |

Module consensus versions are unchanged (30 modules, verified before and after
the upgrade on a local network).

## 2. Fixed advisories

This is a mandatory security upgrade. Details on the fixed advisories will be
published after the upgrade.

## 3. ⚠️ Do not touch `/lib/libwasmvm.x86_64.so`

The running v1.0.1 binary loads libwasmvm 2.1.2 from the unversioned system
file `/lib/libwasmvm.x86_64.so`. On Ubuntu this is the same file as
`/usr/lib/libwasmvm.x86_64.so`, where `medasdigital_setup.sh` installs it.

- **Do NOT replace, update or delete this file**, neither before nor during nor
  right after the upgrade.
  - v1.0.1 needs it until the upgrade height.
  - A rollback to v1.0.1 would need it too.
  - A v2.2.x library in that place would break v1.0.1.
- The v2 binary is statically linked and does not use the file at all. Check:

  ```sh
  ldd medasdigitald        # -> "not a dynamic executable"
  ```

- Only remove the file after the network has run on v2 for a while and nothing
  on the host runs v1.0.1 any more.

## 4. Build and verify the binary

The release binary is built reproducibly in Docker. Everything is pinned: the
Go image by digest, the Alpine packages by exact version, libwasmvm_muslc by
its sha256, and the Go modules by `go.sum`. The same commit therefore gives
the same binary on every machine.

```sh
git clone https://github.com/oxygene76/medasdigital-2 && cd medasdigital-2
git checkout <release tag>
make build-release VERSION=<release tag>      # needs Docker with buildx
cat build/release/medasdigitald.sha256        # compare with the release notes
```

Or download the binary from the GitHub release and compare its checksum:

```sh
sha256sum medasdigitald
```

Expected output of the v2 binary:

```sh
medasdigitald version --long | grep -E '^(version|commit|build_tags|go):'
#   build_tags: netgo ledger muslc,
#   go: go version go1.26.8 linux/amd64
#   version: <release tag>
medasdigitald version --long | grep -E 'cosmos-sdk@|cometbft@|wasmd@|wasmvm|ibc-go/v8@'
#   cometbft@v0.38.26  cosmos-sdk@v0.50.15  wasmd@v0.54.10  wasmvm/v2@v2.2.9  ibc-go/v8@v8.8.0
medasdigitald query wasm libwasmvm-version        # 2.2.9 (no node needed)
ldd medasdigitald                                 # not a dynamic executable
```

## 5. Wasm cache and disk space

- v2 compiles contracts with a newer Wasmer into a new cache directory:
  `<home>/wasm/wasm/cache/modules/3858fb5318-wasmer24/…`. The old directory
  `…/v10-wasmer7/…` is left untouched.
- Contracts are recompiled on their first use after the upgrade. The first
  calls are slower, the results are the same.
- The Wasm data (contract code and cache) lives in `<home>/wasm`, **not** in
  `<home>/data`. Backups and data copies must include both.
- The old cache directory can be deleted once a rollback to v1.0.1 is no longer
  an option.
- The `[wasm]` settings in `app.toml` (`query_gas_limit`, `memory_cache_size`,
  `simulation_gas_limit`) keep their names and meaning.

## 6. Upgrade procedure without Cosmovisor

Reference layout: systemd service `medasdigitald`, binary
`/usr/local/bin/medasdigitald`, home `/root/.medasdigital`, as set up by
`medasdigital_setup.sh`.

**Before the upgrade height:**

```sh
# put the v2 binary next to the running one, do NOT replace it yet
install -m 0755 medasdigitald /usr/local/bin/medasdigitald-v2
/usr/local/bin/medasdigitald-v2 version --long | head     # checks from section 4
df -h /root/.medasdigital                                 # room for a backup?
```

**At the upgrade height**, v1.0.1 logs the following line and stops producing
blocks:

```
ERR UPGRADE "v2" NEEDED at height: <H>: module=x/upgrade
ERR CONSENSUS FAILURE!!! ...
```

The process keeps running, so systemd still shows the service as "active".
Watch the log, not the service state:

```sh
journalctl -fu medasdigitald | grep --line-buffered 'UPGRADE "v2" NEEDED'
```

**Then:**

```sh
systemctl stop medasdigitald
# recommended: backup of data AND wasm (needs roughly the size of the node data)
tar -C /root/.medasdigital -cf /backup/medasdigital-pre-v2.tar data wasm
cp /usr/local/bin/medasdigitald /usr/local/bin/medasdigitald-v1.0.1
install -m 0755 /usr/local/bin/medasdigitald-v2 /usr/local/bin/medasdigitald
# NOT touching /lib/libwasmvm.x86_64.so (section 3)
systemctl start medasdigitald
journalctl -fu medasdigitald
```

**Expected in the log:**

```
INF applying upgrade "v2" at height: <H> module=x/upgrade
INF running upgrade handler height=<H> upgrade=v2
```

Blocks resume as soon as validators with more than 2/3 of the voting power run
v2.

**Checks:**

```sh
medasdigitald version                                   # v2 release tag
medasdigitald q upgrade applied v2 -o json | jq .height # = <H>
medasdigitald q wasm libwasmvm-version                  # 2.2.9
medasdigitald status | jq .sync_info
```

## 7. Upgrade procedure with Cosmovisor

Directory layout under `DAEMON_HOME=/root/.medasdigital`:

```
cosmovisor/genesis/bin/medasdigitald        # v1.0.1 (current binary)
cosmovisor/upgrades/v2/bin/medasdigitald    # v2 (static)
```

Environment:
- `DAEMON_NAME=medasdigitald`, `DAEMON_HOME=/root/.medasdigital`
- `DAEMON_ALLOW_DOWNLOAD_BINARIES=false`, `DAEMON_RESTART_AFTER_UPGRADE=true`
- Cosmovisor's automatic backup copies the whole `data` directory, which is over
  200 GB on the validators. Either provide the space or set
  `UNSAFE_SKIP_BACKUP=true` and make your own backup (section 6).

At the upgrade height Cosmovisor sees `data/upgrade-info.json`, stops v1.0.1 and
starts `upgrades/v2/bin/medasdigitald`. Section 3 applies unchanged: the genesis
binary v1.0.1 keeps using `/lib/libwasmvm.x86_64.so`, and the v2 binary does not
use it. Check afterwards as in section 6.

A separate runbook covers switching an existing systemd service to Cosmovisor.

## 8. If something goes wrong

- **v2 does not start** (e.g. wrong binary). Check the checksum and
  `version --long`, then fix the binary. Do not start v1.0.1 again. After the
  upgrade height it refuses to process blocks:
  `wrong app version 0, upgrade handler is missing for v2 upgrade plan`.
- **v2 was started before the upgrade height.** It logs
  `BINARY UPDATED BEFORE TRIGGER!` and commits nothing. Switch back to v1.0.1
  until the halt.
- **Network-wide rollback.** Only by coordinated decision of the validators:
  1. restore the backup,
  2. restore v1.0.1 (and its system library, which must still be in place),
  3. start with `--unsafe-skip-upgrades <H>`.

## 9. New nodes syncing from genesis

v2 cannot replay blocks from before the upgrade height. A node syncing from
genesis runs v1.0.1 up to the upgrade height and then switches to v2, or it uses
state sync / a snapshot taken after the upgrade.

`medasdigital_setup.sh` installs the binary of the **latest** GitHub release.
Once a v2 release is published, the script must not be used for syncing from
genesis without adjustment.
