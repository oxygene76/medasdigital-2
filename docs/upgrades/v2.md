# Mandatory security upgrade `v2`

| | |
|---|---|
| Upgrade name | `v2` |
| Upgrade height | **_to be announced_** (set by the governance proposal) |
| Expected date | **_to be announced_** |
| New version | `v2.0.0` |
| Type | **mandatory security upgrade**: no new features, no parameter or state changes |

The v2 software fixes security issues in the dependencies of v1.0.1. Details on
the fixed advisories will be published after the upgrade.

The switch is coordinated by height:
- **v1.0.1 stops at the upgrade height.**
- v2 refuses to run before it.

Every node, validators and full nodes alike, must switch to v2 at the upgrade
height. The chain continues as soon as validators with more than 2/3 of the
voting power run v2.

Check the scheduled height at any time:

```sh
medasdigitald query upgrade plan
```

## 1. What changes

| Component | v1.0.1 (current) | v2.0.0 |
|---|---|---|
| Cosmos SDK | v0.50.10 | v0.50.15 |
| ibc-go | v8.5.1 | v8.8.0 |
| CometBFT | v0.38.21 | v0.38.26 |
| wasmd | v0.53.0 | v0.54.10 |
| wasmvm / libwasmvm | 2.1.2, dynamically linked | 2.2.9, **statically linked** |
| Go | 1.22.11 | 1.26.8 |
| Binary | dynamic (glibc) | **static** (musl) |

- The upgrade handler runs no state migrations; all module versions stay the same.
- Configuration files keep their format. This includes the `[wasm]` settings in
  `app.toml`.

## 2. The v2 binary and its checksum

The v2 binary will be published as GitHub release
[`v2.0.0`](https://github.com/oxygene76/medasdigital-2/releases) together with
its checksum:

| | |
|---|---|
| File | `medasdigitald` (linux/amd64, static) |
| SHA-256 | `1158578518b024dc4b44ea6ea77584a6186463b3fbf6451e3713932fa50e26d2` |

The binary is built reproducibly from tag `v2.0.0`; see
[docs/building.md](../building.md). Verify the download:

```sh
sha256sum medasdigitald                                   # must match the release
./medasdigitald version                                   # v2.0.0
ldd ./medasdigitald                                       # not a dynamic executable
./medasdigitald query wasm libwasmvm-version              # 2.2.9
```

## 3. ⚠️ Do NOT replace `/lib/libwasmvm.x86_64.so`

v1.0.1 loads libwasmvm **2.1.2** from the system file
`/lib/libwasmvm.x86_64.so`. On Ubuntu that is the same file as
`/usr/lib/libwasmvm.x86_64.so`.

- **Do not replace, update or delete this file**, not before, not during and
  not right after the upgrade.
  - v1.0.1 needs it until the upgrade height.
  - A rollback would need it too.
  - A newer libwasmvm in its place would break v1.0.1 immediately.
- v2 is statically linked and does not use this file at all. No library needs to
  be installed for v2.
- Remove the file only when nothing on the machine runs v1.0.1 any more.

## 4. Upgrade with Cosmovisor (recommended)

Nodes set up with [`medasdigital_setup.sh`](../../medasdigital_setup.sh) already
run under Cosmovisor. Cosmovisor switches to v2 automatically at the upgrade
height; no manual action is needed at that moment.

**Existing nodes without Cosmovisor:** switch now, well before the upgrade height:

```sh
sudo ./medasdigital_setup.sh migrate
```

On a validator, `migrate` shows the voting power and the allowed downtime before
switching. It also prints a rollback. See the
[README](../../README.md#existing-nodes-switch-to-cosmovisor).

**Prepare the upgrade.** As soon as the v2 release is published:
1. Download the setup script version that lists the v2 binary.
2. Run:

   ```sh
   sudo ./medasdigital_setup.sh prepare-upgrade v2   # downloads and verifies v2 into cosmovisor/upgrades/v2/bin
   ./medasdigital_setup.sh status
   ```

`status` must show `Prepared upgrade : v2 (v2.0.0)`. The following warning means
the node is not ready:

```
WARNING: Upgrade 'v2' is scheduled but NOT prepared
```

**Before the upgrade height:** take a VM snapshot or a backup. The service
created by the setup script skips Cosmovisor's own backup
(`UNSAFE_SKIP_BACKUP=true`), because that would copy the whole data directory at
the upgrade height.

**At the upgrade height:** nothing to do. Watch the log:

```sh
journalctl -fu medasdigitald
```

Expected sequence:

```
ERR UPGRADE "v2" NEEDED at height: <height>
INF upgrade detected, relaunching ... module=cosmovisor
INF applying upgrade "v2" at height: <height>
INF upgrade handler finished ...
```

## 5. Upgrade without Cosmovisor

1. **Before the upgrade height:** download and verify the v2 binary (section 2)
   and place it next to the current one. Do not replace the current binary yet.

   ```sh
   sudo install -m 0755 medasdigitald /usr/local/bin/medasdigitald-v2
   ```

2. **At the upgrade height**, v1.0.1 logs the following and stops processing
   blocks:

   ```
   ERR UPGRADE "v2" NEEDED at height: <height>
   ERR CONSENSUS FAILURE!!! ...
   ```

   The process keeps running, so systemd still shows the service as active.
   Watch the log, not the service state.

3. **Switch:**

   ```sh
   sudo systemctl stop medasdigitald
   # optional backup of data/ and wasm/ in the node home
   sudo cp /usr/local/bin/medasdigitald /usr/local/bin/medasdigitald-v1.0.1
   sudo install -m 0755 /usr/local/bin/medasdigitald-v2 /usr/local/bin/medasdigitald
   # do NOT touch /lib/libwasmvm.x86_64.so (section 3)
   sudo systemctl start medasdigitald
   journalctl -fu medasdigitald    # expect: applying upgrade "v2" at height: <height>
   ```

Things that go wrong:
- **v2 before the upgrade height** logs `BINARY UPDATED BEFORE TRIGGER!` and
  commits nothing. Switch back to v1.0.1 until the halt.
- **v1.0.1 after the upgrade height** refuses to process blocks
  (`upgrade handler is missing for v2 upgrade plan`).

## 6. Checks after the upgrade

```sh
medasdigitald version                                    # v2.0.0
medasdigitald query upgrade applied v2 -o json | jq .height   # the upgrade height
medasdigitald query wasm libwasmvm-version               # 2.2.9
medasdigitald status | jq .sync_info                     # height grows, catching_up false
```

The node home contains a second Wasm cache directory after the upgrade:
- v2 compiles contracts with a newer Wasm engine into
  `<home>/wasm/wasm/cache/modules/`.
- The old cache directory stays untouched and can be deleted once a rollback is
  no longer an option.
- The first contract calls after the upgrade are slower because the contracts
  are recompiled.

## 7. New nodes after the upgrade

v2 cannot replay blocks from before the upgrade height. New nodes:
- start with state sync from a snapshot taken after the upgrade, or
- sync from genesis with v1.0.1 as the Cosmovisor genesis binary and v2
  prepared for the switch.

`medasdigital_setup.sh` handles both cases.
